# 03 — Refined product design proposal (V2)

Date: 2026-11-24. Status **PROPOSED / DISCOVERY — requires owner review before implementation**. This is a design-level review, not executed tests, live-model evaluation or approved schema migration.

## 1. Product decision
The primary feature is faithful reconstruction of external narrative into a normal Proactive Co-Creator workspace, with source-supported findings, explicit user authority and retained audit records. Optional enhancement is a separate proposal stage, not a hidden rewrite. Existing backup restoration is deterministic and AI-free. Preserve forward creation, current graph/Bible/decisions, generation modes, data integrity and old backups. No user is required to use a wizard to start a normal idea project.

Workspace: existing Story Bible, Belief Graph, Decisions, Checks, Output, Revision History and Evidence & Audit views, with contextual links. App Settings global and distinct from project backups. ## 4. Evidence & Audit — a single source of truth
Three distinct concepts:
- Evidence: source passage anchored to immutable source revision.
- Rationale: concise explanation of extraction/interpretation/decision, not unverifiable private model thinking.
- Change audit: immutable event recording proposal, actor (AI/user/system), accepted/rejected/deferred/apply/undo, before/after, reason, linked source/issue and project revision.
One registry, multiple views/exports. Do not ask AI to independently produce a JSON file and a Markdown report. AI returns schema-constrained proposals; application validates and deterministically renders JSON plus Markdown from the same record IDs. Optional original source export and a ZIP export bundle later. Reports should indicate revision and filters; provide full export and selected records, consistent redaction and no keys/internal prompts. Evidence exports can contain private manuscript passages; explicit download and privacy notice. Preserve original source and extraction provenance after import. Show contextual evidence icon/“View source” on major graph/Bible/relationship/issue items and searchable Evidence & Audit view with filters by category, source, confidence/status, changed/current/stale.

Proposed records (conceptual, not final TS or schema):
- SourceDocumentVersion: sourceId, versionId, name, format, importedAt, original/normalized-text hash, parser version, original file retention policy, exact extracted text and structural block IDs. Chapter heading if real, paragraph number if real; otherwise block/line/span location; no invented chapter metadata. Offsets explicitly measured in UTF-16 code units on immutable normalized text (or another single documented coordinate system); stable block-relative offsets and exact excerpt/hash. Preserve mappings when normalization differs. No automatic fetch of external URLs.
- Claim: stable claimId, target kind/id/field, value/direction, sourceRefs[], evidenceKind, attribution (narrator/character/report/unknown), scope/time, short rationale, approval status, extraction run/version/model ID and freshness. Relation evidenceExcerpt alone insufficient. Evidence kind and approval independent; actual quote existence verified programmatically, entailment still fallible; inference/ambiguous claims require review. User-authored claim can have user rationale rather than fake source. Do not invent model confidence percentages.
- Issue: issueId, type, severity, certainty, affected claim IDs, multiple evidence refs, rationale, status, resolution event link, first/last seen and project/source version. Distinguish evidence conflict from deliberate ambiguity, temporal change, flashback or different speaker.
- AuditEvent: eventId, actor, action, timestamp, proposal/claim/issue refs, before/after values or patch ref, rationale, base/result revision, source refs. Append-only logically; undo adds event rather than deleting history. Audit cannot promise tamper-proof security on local client. Mark current state separately; retention/export policy explicit, not infinite duplicated snapshots.
- ImportRun: runId, source version hashes, options, instructions (user-facing), model/provider/version, coverage chunks, warnings, budget/usage, state and commit id; avoid retaining secrets or unnecessary raw AI logs.

Evidence scope: cite every imported substantive canonical entity/property/relation/Story Bible fact and every flagged issue or applied AI change. Group repeated support and reuse references; don't generate verbose explanations for trivial formatting/system-generated IDs. Preserve minimal evidence even if UI collapses details. Unknown values remain unknown; no forced 3–4 attributes, implicit new entities or made-up alternatives in faithful mode. Distinguish direct statements from what a character believes and what narrator implies. Separate inferred themes, genre, motives, intended audience. Example: Leyla childhood friend of Murat → exact source phrase; “Murat hid letters because of guilt” unsupported, not a fact. If no evidence or ambiguous identity, pending or omit, not confirmed. If source changed, old evidence remains historical and current claim marked needs revalidation. Identity merges use stable IDs and alias references, uncertain merges review, not name-only equality.

## 5. Import stages and modes
Recommended 5 logical stages (may render as 4 wizard screens):
1. Select source/paste TXT, MD, DOCX. Local safe parsing/preview, byte and decompressed size checks, no AI call and no project mutation. Show structure, word/character count, missing content warnings and extraction limitations. DOCX tracked changes/notes/tables policy explicit; do not claim exact visual formatting reconstruction. No external link resolution, active content or execution.
2. Configure: primary mode Faithful Reconstruction or Reconstruct & Enhance; extraction scope Full or Selective (orthogonal to strategy, unlike V1's three competing radio choices). Optional analysis instructions, language, scope, provider disclosure and estimated processing budget. Faithful ignores requests to alter source with clear explanation; require mode switch or separate post-import edit.
3. Analyze: explicit user action; segment with headings/blocks, bounded chunk calls, deduplicate overlap, identity resolution, global synthesis and validation; progress from completed work, coverage/missing chunks, real errors, cancel, retry only failed stage where safe. No uncontrolled retries or hidden new costs. Draft proposal isolated from existing project. No free/paid service claims without verification.
4. Review: source-supported, interpretations, ambiguities/conflicts, issues and optional enhancements shown separately. User can edit extraction if misread, accept selected or supported group, reject, defer all unresolved or request clarification. In faithful mode extraction correction is correction of representation only, not rewriting story; no creative suggestions or story corrections. Enhancement mode may request separate AI proposal to change working narrative/canonical representation; show source, exact target and before/after, risks, explanation. Require approval before apply. Skipping review does not authorize changes. “Defer all” stores unresolved findings, excludes pending from confirmed generation context; “Ignore” ambiguous label avoided. Major safety blockers (invalid file, missing coverage, invalid identity references, failed persistence) cannot be bypassed by bulk skip; optional partial import only explicit, visible incomplete state, no false complete claim. Preview counts from validated proposal, not invented metrics.
5. Create Project: explicit final confirmation, fresh project ID, deterministic assembly from accepted and pending separated, initial audit/revision link, durable commit via storage authority; show success only after successful persistence or explicit recovery status. Failure leaves original and prior projects intact and proposal recoverable. Cancel/late result cannot mutate active project. On commit, open workspace with unresolved issue count and evidence navigation. No generation call by default. User-selected original source retained separately; short working idea/context summary not the full manuscript. Default new project; existing-project append remains open later scope requiring revision/CAS and conflict review.

Faithful = source reconstruction, not new narrative; still flags possible problems and unsupported interpretations, does not invent repairs. Enhancement = first faithful extraction, then optional explicit proposals and approved change transaction; not default. Selective = what to analyze regardless of mode. Existing generation analysis retains its creative semantics; no regression.

## 6. Persistent issue lifecycle
Suggested UI labels/status:
- Open (including possible inconsistency): requires attention; flag severity without claiming all anomalies are errors.
- Deferred / Review Later: remains unresolved, visible count, optional filter; no promise of scheduled notifications.
- Needs Clarification: ask for user context with source refs, keep original.
- Proposed Fix: proposed change not yet applied, may be rejected, stale or superseded.
- Resolved: actual approved change or user clarification resolves condition, record why; revalidate against current source/canonical state.
- Dismissed / Intentional: user explicitly classifies as not a problem with optional reason; distinguish from resolved by correction, keep audit and allow reopen.
Possible issue types: timeline, name/alias identity, relationship direction/role, incompatible attributes, continuity/location, narrative POV/tense, missing evidence, missing/incomplete extraction. Separate changes over time from contradictions; preserve quoted speech and narrator reliability.

Example: text says a letter was written three years after mother's death. Does not establish mother authored it; mark question/possible chronology issue, not factual contradiction. If user says intentional mystery, record dismissal/intentional; if user says date typo, enhancement/post-import fix proposal with original and new date, reason and evidence. Applying only modifies intended canonical fields and/or working manuscript, not original source. Existing app has story artifacts, not a versioned manuscript editor; source text rewriting requires explicit working-copy data model, preview and patch application. MVP can fix graph/Bible representation or create a proposed patch/export only; never imply original prose fixed if only graph changed. Track separate target kind; user manual edit or AI-assisted edit uses same authority and transaction. On successful fix update issue state, retain original, show correction record and “View changes”; revert via safe transaction or revision checkpoint, detect stale/dependent changes, re-open if contradiction returns. Do not silently mark resolved because AI claims so. Distinguish revision History (snapshots/recovery) from issue state and audit events (why/what/when). Re-run affected checks after edits, not whole manuscript blindly.

## 7. Length policy — replace 8000, not safeguards
Current source: shared/schemas.ts:18–65 MAX_PROMPT_CHARS=8000, multiple request schemas, batch-edit prompt cap; App.tsx preflight length checks; Express global JSON limit 1mb; promptBuilder compiles seed, graph/Bible/notes. These are application guards, not proof of Gemini context limit. Stage 0 already measured compiled prompt can exceed cap. Owner wants unrestricted writing/import, not hidden deletion. Remove arbitrary author-facing hard character limit where safe; allow writing/saving long local source within published storage constraints. Distinguish manuscript ingest limits from AI operations (analyze, clarify, polish, batch, generate text/image). Do not just delete MAX_PROMPT_CHARS or raise Express globally. Tokenize/estimate per provider/model and operation, verify actual API input/output/combined context limits at implementation time, reserve instructions/schema/output/reasoning budget, budget total tokens/calls, rate/concurrency/retry caps and user-visible cost/usage. Provider-dependent pricing: https://ai.google.dev/gemini-api/docs/pricing ; model/token documentation: https://ai.google.dev/gemini-api/docs/tokens and https://ai.google.dev/gemini-api/docs/models . No claimed tested model limit or price here. Local file byte and decompress bounds, per-chunk request cap under server body limits, segmentation by semantic blocks, overlap tracked, coverage map, identity merge, bounded global summaries with source anchors. For generation select relevant confirmed context, not whole novel every time; expose what was sent/omitted, warn user if incomplete, preserve entire source. If budget exceeds or model unavailable, propose chunking/scoping/explicit consent; never silently truncate or overwrite. Distinguish actual observed token usage from estimates. Confirm privacy/provider handling before upload; avoid storing manuscript in server logs and repeated transmission where not needed. Benchmark Turkish/English/multilingual token distribution, graph sizes, browser storage quota, latency and cost before choosing numeric thresholds. No unlimited service promise.

## 8. Export and persistence
Structured JSON is AI-readable and validated, Markdown human-readable. Both are deterministic projections of the same versioned records, not independent model outputs. Suggested exports:
- Original source text (and original file if retention option enabled; fidelity distinction explicit)
- Working manuscript/story (if supported and selected), generated story, Story Bible, refined prompt
- Evidence report (.md/.json)
- Issues report (.md/.json), including open/deferred/dismissed/resolved and before/after
- Change audit (.md/.json) with optional per-run filters
- Full Project Backup (.json or explicitly versioned bundle) containing everything needed to restore claimed scope
Avoid seven mandatory downloads; one Export dialog with content selection and format, optional evidence bundle. Audit/export of current view must explicitly say filtered vs complete. JSON export version, stable IDs and source digest; Markdown sections and readable excerpts. No conflation with backup. Store source blobs once outside snapshot copies; evidence refs and event log version-aware. Schema3 currently no source registry; new model may require schema4 or backward-compatible extension with explicit migration and validation, not simply add optional fields and assume survives normalization. Evaluate IndexedDB transactional storage, compatibility/cache limits, failure recovery, source deletion and retention, backup/restore roundtrip; no cloud or new DB commitment. Unresolved user review: original DOCX bytes optional vs mandatory vs extracted text only; product must never label extracted-only as original DOCX backup. Data size tests on representative novels. Audit events can be compact; preserve user-created decisions and explain retention limits.
